Jarvis · architecture · draft 2026-10-26

How Jarvis works

A personal development agent on the owner's laptop. A task arrives in chat, Jarvis takes it to a verified draft PR and follows it until CI is green and the review is approved. All model calls go through the claude CLI on the Max subscription, with no API key.

Components

Everything runs on a single laptop. The engine is the only process that controls the system. Claude does the substantive work, but changes state only through tools the engine provides.

Engine

Plain code

Receives messages, stores state, launches Claude, watches GitHub, streams events to the web. It does not “think” itself.

Dispatcher

One session per thread

Each of your messages triggers a short run that resumes the thread's session. It understands the request, creates and manages tasks, and replies. It does not write code.

Worker

One process per task stage

Works in the task's git worktree: context, spec, plan, code, checks, review, PR. No process exists between stages; the session is resumed.

Watcher

Polls GitHub

Once a minute: CI, reviews, comments. It never runs the model. It wakes the worker only when something changed.

Jarvis MCP

Capability boundary

Tools per role: create_task, report_stage, ask_owner, approve… There is no tool for merge or push to main.

Web

Chat and admin

Threads, decision and permission cards, tasks, artifacts, live run consoles, limits, connections.

While a task waits for you, CI or review, no Claude process runs and no limits are spent. Your message sent while the worker is running goes to its stdin; otherwise it waits for the next run.

Task states

stateDiagram-v2
    [*] --> Intake
    Intake --> Context
    Context --> SpecReview: spec and plan ready
    SpecReview --> Context: owner comment
    SpecReview --> Implementing: Approve
    Implementing --> Verifying
    Verifying --> Implementing: check red (up to 3 attempts)
    Verifying --> Reviewing
    Reviewing --> Implementing: blocking comment
    Reviewing --> PROpen: draft PR
    PROpen --> Fixing: CI failed / comment
    Fixing --> PROpen: new commit
    PROpen --> Done: CI green + approve
    Context --> Blocked: question or no access
    Implementing --> Blocked: question
    Blocked --> Context: answer
    Verifying --> Failed: attempts exhausted
    Fixing --> Blocked: rounds exhausted
    Done --> [*]

A task can be cancelled (Cancelled) from any state: the branch and PR remain. Only states where a process is actually running occupy a worker slot.

Where data lives

Data is split by who changes it and whether it can be shared. The agent definition is in git and can be shown to participants. Personal and working data live in ~/.jarvis, outside the repository. State is in Postgres. Session transcripts are stored by Claude Code itself.

1. Agent definition git · repo jarvis

Who Jarvis is and how it works. It is a Claude Code plugin that the engine attaches to every run via --plugin-dir.

3. State Postgres · Docker

Threads, messages, tasks, journal, runs and every run event, permissions, PR watch state, usage. Details below.

4. Claude sessions ~/.claude · managed by Claude Code

Transcripts in ~/.claude/projects/<folder>/<session>.jsonl and the subscription login (Keychain). Jarvis stores only the session_id. A session is bound to the launch folder, so the dispatcher always starts from ~/.jarvis/dispatcher and the worker from its own worktree.

5. Project rules target repository

AGENTS.md with check and dev-server commands, conventions, CI. The worker reads them from its worktree. Project rules are not mixed with the owner's profile.

6. External output GitHub

jarvis/* branches, draft PRs, comments and commits from the Jarvis account. This is what other people see.

claude runs start with --setting-sources project,local: your personal plugins, skills and hooks from ~/.claude do not reach the agent. It sees only the Jarvis plugin, the target repository's rules and the MCP servers from --mcp-config (with --strict-mcp-config).

There are no secrets in the database. Run events pass through a redactor that strips tokens before they are written to the database or sent to the web.

How Claude is launched

Dispatcher run 
cd ~/.jarvis/dispatcher
claude -p "<message>"
  --resume <thread-session>
  --output-format stream-json --verbose
  --plugin-dir agent/ --setting-sources project,local
  --append-system-prompt-file agent/prompts/dispatcher.md
  --mcp-config runs/R-n/mcp.json --strict-mcp-config
  --permission-prompt-tool mcp__jarvis__approve
  --model sonnet --max-turns 15
Worker run 
cd ~/.jarvis/worktrees/T-1
claude -p --resume <task-session>
  --input-format stream-json --output-format stream-json --verbose
  --plugin-dir agent/ --setting-sources project,local
  --append-system-prompt-file agent/prompts/worker/<stage>.md
  --settings runs/R-n/settings.json
  --mcp-config runs/R-n/mcp.json --strict-mcp-config
  --permission-prompt-tool mcp__jarvis__approve
  --model sonnet --max-turns 60 --max-budget-usd 3

The engine passes child processes only the variables they need: the worker gets GH_TOKEN and connector tokens, the dispatcher gets nothing. If ANTHROPIC_API_KEY is present in the environment, the engine refuses to start, because otherwise -p would silently switch to API billing.

The onion rule

  • The domain knows nothing about the DB, processes or HTTP — the state machine and limits are tested without the outside world.
  • Use cases talk to the outside world only through ports.
  • claude, git, gh are run only in infrastructure.
  • Slack in iteration 2 is just another adapter in presentation next to the web; the domain and use cases do not change.

Safety and limits

What the agent can and cannot do

  • Changes files only in its own worktree.
  • Pushes only to jarvis/*; push to the base branch, force-push and merge are denied in settings and have no tools.
  • Any other action outside the allowlist produces an Allow / Deny card in the thread; with no answer it is denied on timeout.
  • Text from PRs, Notion and CI logs is data, not instructions.
  • PR comments are honored only from people on the allowlist.

Limits for Max 5x · jarvis.config.json

  • 1 worker at a time (2 possible).
  • 3 check attempts, 2 CI rounds, 3 review rounds.
  • Per run: 60 turns and $3 by the CLI estimate.
  • $20 per day: after that new runs are paused, with a banner in the web.
  • The watcher polls GitHub every 60 s without the model.

Dollars are a CLI estimate, not the subscription meter. It is a brake, not precise accounting.
