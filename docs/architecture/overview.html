Як працює Jarvis

Персональний агент для розробки на ноутбуці власника. Задача приходить у чат, Jarvis доводить її до перевіреного draft PR і супроводжує, доки CI зелений і рев'ю схвалене. Усі виклики моделі йдуть через CLI claude на підписці Max, без API-ключа.

Складові

Усе працює на одному ноутбуці. Engine — єдиний процес, який керує системою. Claude робить змістовну роботу, але змінює стан лише через інструменти, які дає engine.

Engine

Звичайний код

Приймає повідомлення, зберігає стан, запускає Claude, стежить за GitHub, стрімить події у веб. Сам не «думає».

Dispatcher

Одна сесія на тред

На кожне ваше повідомлення — короткий запуск, що продовжує сесію треду. Розуміє запит, створює й веде задачі, відповідає. Код не пише.

Worker

Процес на етап задачі

Працює в git worktree задачі: контекст, spec, план, код, перевірки, рев'ю, PR. Між етапами процесу немає, сесія відновлюється.

Watcher

Опитує GitHub

Раз на хвилину: CI, рев'ю, коментарі. Модель не запускає. Будить воркера лише коли щось змінилось.

Jarvis MCP

Межа можливостей

Інструменти на роль: create_task, report_stage, ask_owner, approve… Інструмента для merge чи push у main немає.

Web

Чат і адмінка

Треди, картки рішень і дозволів, задачі, артефакти, живі консолі запусків, ліміти, підключення.

Поки задача чекає вас, CI або рев'ю, жоден процес Claude не працює і ліміти не витрачаються. Ваше повідомлення під час роботи воркера йде йому в stdin, інакше чекає наступного запуску.

З будь-якого стану задачу можна скасувати (Cancelled): гілка й PR лишаються. Слот воркера займають лише стани, де процес справді працює.

Де живуть дані

Дані розкладені за тим, хто їх змінює і чи можна ними ділитися. Визначення агента — у git, його можна показати учасникам. Особисте й робоче — у ~/.jarvis, поза репозиторієм. Стан — у Postgres. Транскрипти сесій зберігає сам Claude Code.

1. Визначення агента git · repo jarvis

Хто такий Jarvis і як він працює. Це плагін Claude Code, який engine підключає до кожного запуску через --plugin-dir.

2. Особисте і робоче ~/.jarvis · поза git

Вподобання, конфіг, секрети й усе, що агент створює під час роботи.

3. Стан Postgres · Docker

Треди, повідомлення, задачі, журнал, запуски та кожна подія запуску, дозволи, стан нагляду за PR, використання. Деталі нижче.

4. Сесії Claude ~/.claude · керує Claude Code

Транскрипти ~/.claude/projects/<папка>/<session>.jsonl і вхід у підписку (Keychain). Jarvis зберігає лише session_id. Сесія прив'язана до папки запуску, тому диспетчер завжди стартує з ~/.jarvis/dispatcher, а воркер — зі свого worktree.

5. Правила проєкту цільовий репозиторій

AGENTS.md з командами перевірок і dev-сервера, конвенції, CI. Воркер читає їх зі свого worktree. Правила проєкту не змішуються з профілем власника.

6. Зовнішній результат GitHub

Гілки jarvis/*, draft PR, коментарі й коміти від акаунта Jarvis. Це те, що бачать інші люди.

Запуски claude стартують з --setting-sources project,local: ваші особисті плагіни, скіли й хуки з ~/.claude не потрапляють в агента. Він бачить лише плагін Jarvis, правила цільового репозиторію й MCP-сервери з --mcp-config (з --strict-mcp-config).

Секретів у базі немає. Події запусків проходять через редактор, який вирізає токени, перш ніж записати їх у базу чи відправити у веб.

Як запускається Claude

Dispatcher run 
cd ~/.jarvis/dispatcher
claude -p "<повідомлення>"
  --resume <thread-session>
  --output-format stream-json --verbose
  --plugin-dir agent/ --setting-sources project,local
  --append-system-prompt-file agent/prompts/dispatcher.md
  --mcp-config runs/R-n/mcp.json --strict-mcp-config
  --permission-prompt-tool mcp__jarvis__approve
  --model sonnet --max-turns 15
Worker run 
cd ~/.jarvis/worktrees/T-1
claude -p --resume <task-session>
  --input-format stream-json --output-format stream-json --verbose
  --plugin-dir agent/ --setting-sources project,local
  --append-system-prompt-file agent/prompts/worker/<stage>.md
  --settings runs/R-n/settings.json
  --mcp-config runs/R-n/mcp.json --strict-mcp-config
  --permission-prompt-tool mcp__jarvis__approve
  --model sonnet --max-turns 60 --max-budget-usd 3

Engine передає дочірнім процесам лише потрібні змінні: воркеру GH_TOKEN і токени конекторів, диспетчеру нічого. Якщо в середовищі є ANTHROPIC_API_KEY, engine не стартує, бо інакше -p мовчки перейшов би на оплату за API.

Правило onion

  • Домен не знає про БД, процеси й HTTP — стейт-машина й ліміти тестуються без зовнішнього світу.
  • Сценарії говорять із зовнішнім світом лише через порти.
  • claude, git, gh запускаються тільки в infrastructure.
  • Slack в ітерації 2 — ще один адаптер у presentation поруч із вебом; домен і сценарії не змінюються.

Безпека і ліміти

Що агент може і не може

  • Змінює файли лише у своєму worktree.
  • Пушить лише в jarvis/*; push у базову гілку, force-push, merge заборонені в settings і не мають інструментів.
  • Решта дій поза allowlist — картка Allow / Deny у треді; без відповіді — відмова за таймаутом.
  • Текст із PR, Notion, логів CI — дані, а не інструкції.
  • Коментарі в PR враховуються лише від людей з allowlist.

Ліміти під Max 5x · jarvis.config.json

  • 1 воркер одночасно (можна 2).
  • 3 спроби перевірок, 2 раунди CI, 3 раунди рев'ю.
  • На запуск: 60 кроків і $3 за оцінкою CLI.
  • $20 на день: далі нові запуски на паузі, банер у вебі.
  • Watcher опитує GitHub раз на 60 с без моделі.

Долари — оцінка CLI, а не лічильник підписки. Це гальмо, не точний облік.

Ще не вирішено

  1. Яка демо-задача і в якому репозиторії.
  2. Як воркер отримує дизайн із Claude Design: посилання, handoff чи експорт у репозиторій.
  3. Які MCP-сервери для Notion і Google Docs беремо і які права токенів їм потрібні.
  4. Чи вистачає fine-grained PAT для читання check runs, чи потрібен інший спосіб.
  5. Скільки ліміту Max 5x з'їдає один повний прогін демо-задачі.
  6. Прийняти або змінити ADR-0002…0011.
