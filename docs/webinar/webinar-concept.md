# Концепт вебінару для продажів і маркетингу
## Власний AI-агент для розробки: від задачі до перевіреного pull request

**Статус:** концепт для підготовки вебінару, версія 2. Склад прототипу й архітектура уточнені. Прототип, джерела та матеріали потрібно підготувати й перевірити до анонсу.

**Формат:** практичний вебінар із демонстрацією, розбором технічних рішень і короткою вправою.

**Рівень реалізації:** proof of concept (PoC), навчальний прототип.

**Рекомендована тривалість:** 90 хвилин разом із презентацією курсу та Q&A.

**Основа:** [Jarvis Agent, концепт v0.2](https://claude.ai/artifact/8BzqCfgQC2LsZ8Xw4SLHLn). У версії 2 додано: дизайн із Claude Design як вхід задачі, архітектуру «диспетчер + воркери» на підписці Claude Code, власний Slack-канал, нагляд за CI, адмінку агента, поділ на підготовлене й зроблене в ефірі та розбір технічних челенджів.

## 1. Конкретна ідея агента

Jarvis отримує в Slack задачу: посилання на дизайн у Claude Design і на матеріали в Notion та Google Docs. Він сам знаходить потрібну інформацію, оформлює специфікацію, будує план, реалізує фічу в окремій гілці, проганяє перевірки, робить рев'ю, відкриває pull request і далі стежить за ним: чекає результатів CI, виправляє зауваження рев'юера й надсилає підсумок у Slack.

Усе працює на ноутбуці розробника через його підписку Claude Code. Окремої оплати за API немає.

Профіль агента описує його роль, принципи роботи, вподобання власника та формат результатів. Агент використовує ці налаштування в кожній задачі.

**Основна обіцянка:** показати, як побудувати персонального агента, який бере дизайн і матеріали проєкту, виконує задачу за Spec-Driven Development (SDD), тобто процесом розробки на основі специфікації, і доводить її до перевіреного PR.

Учасник отримує навчальний PoC і може дослідити його складові та повторити демонстрацію.

**Що Jarvis робить у прототипі:**

1. Головний флоу: дизайн і задача → контекст → spec і план → код → перевірки → рев'ю → PR → правки за коментарями → повідомлення в Slack.
2. Нагляд за CI: стежить за перевірками свого PR, розбирає падіння, пробує виправити або повідомляє з поясненням.
3. Паралельна робота: веде до двох задач одночасно, кожну в окремій гілці.
4. Пошук знань: знаходить відповідь у Notion і Google Docs та дає посилання на джерела.

**Дія для користувача:** поставити задачу в Slack, зайнятися іншою роботою й отримати повідомлення, коли є результат, зміна статусу або потрібне рішення.

## 2. Назва та підзаголовок

**Основна назва:** Власний AI-агент для розробки: від задачі до перевіреного pull request

**Підзаголовок:** Збираємо proof of concept персонального агента на підписці Claude Code: він бере дизайн із Claude Design, знаходить контекст у Notion і Google Docs, виконує задачу за специфікацією, стежить за CI та рев'ю і пише вам у Slack.

**Короткий варіант для реклами:** Власний AI-агент, який сам доводить задачу до pull request

Технічні поняття розкриваємо через демонстрацію: що агент знайшов, які рішення прийняв, кому делегував роботу та який результат підготував.

## 3. Для кого

Основна аудиторія: Middle та Senior розробники, які використовують AI та хочуть побудувати власний процес виконання задач із доступом до матеріалів проєкту.

- Для тих, хто працює з AI покроково: як делегувати пошук контексту, підготовку специфікації та подальше виконання.
- Для тих, хто вже створив першого агента: як додати зовнішні джерела, профіль власника, роботу за специфікацією, спеціалізовані ролі й нагляд за CI.
- Для тих, хто розвивається в Agentic Engineering: цілісний приклад, який можна запустити й розібрати, разом із технічними рішеннями та їхніми компромісами.

Потрібне базове розуміння коду, Git і pull request. Для повторення PoC потрібні підписка Claude Code (Pro або Max), GitHub-репозиторій і безкоштовний Slack-воркспейс. Точні вимоги вказуємо в README.

## 4. Біль аудиторії

- Дизайн у Claude Design, вимоги в Notion, додаткові рішення в Google Docs, правила реалізації в репозиторії. Усе це доводиться збирати вручну.
- AI знає лише те, що розробник встиг передати в поточний запит.
- Після кожного уточнення потрібно знову пояснювати, що робити та який результат очікується.
- Власні вподобання щодо планування, запитань і формату відповіді губляться між чатами.
- Уже є окремі агенти, але незрозуміло, як поєднати їх у виконання однієї задачі.
- Під час довгої задачі важко побачити, який контекст використано, що вже виконано та що залишилося.
- Після створення PR доводиться повертатися й перевіряти, чи завершився CI, чи надійшло рев'ю та чи потрібні правки.
- Агент на API коштує грошей за кожен запуск, а з підпискою незрозуміло, як зробити його автономним.

Особиста цінність вебінару: навчитися поєднувати джерела знань, інструменти й агентів у власний процес розробки та отримати робочу основу для експериментів.

## 5. Сценарій, який показуємо

### Приклад задачі для демонстрації

> Додай у навчальний застосунок сторінку програми курсу. Дизайн сторінки за цим посиланням у Claude Design. Структуру та описи занять знайди в Notion. Правила подачі й вимоги до інтерфейсу знайди в Google Docs. Використай компоненти й конвенції репозиторію. Покажи специфікацію та план, реалізуй сторінку і підготуй PR. Стеж за CI та рев'ю, пиши мені в Slack.

Задачу пишемо в Slack. Фінальні вимоги фіксуємо після підготовки дизайну, матеріалів і початкового стану застосунку.

### Що людина передає на вході

- Опис бажаного результату в Slack.
- Посилання на дизайн у Claude Design.
- Посилання на кореневу сторінку курсу в Notion і на папку з Google документами.
- Репозиторій, з яким працює агент (один для демо).
- Профіль агента та власника, підготовлений один раз.

### Що агент робить сам

1. Диспетчер приймає задачу в Slack, записує її в стан і створює окремий worktree (окрему робочу копію репозиторію) та гілку.
2. Запускає воркера, окрему сесію Claude Code для цієї задачі.
3. Воркер забирає дизайн, через конектори читає Notion і Google Docs, аналізує репозиторій.
4. Пише `context.md` з джерелами та відкритими питаннями, потім `spec.md` з критеріями приймання.
5. Готує `plan.md` і `tasks.md`. Диспетчер надсилає spec і план у Slack на підтвердження.
6. Після підтвердження реалізує фічу та оновлює статуси задач.
7. Запускає тести, lint і typecheck. Якщо перевірка червона, виправляє, максимум три спроби.
8. Окремий агент-рев'юер перевіряє зміни на відповідність spec і правилам репозиторію.
9. Відкриває draft PR і пише `result.md`.
10. Watcher (скрипт без моделі) стежить за CI і рев'ю PR та будить диспетчера, коли статус змінився.
11. Якщо CI впав, воркер читає лог і пробує виправити. Якщо рев'юер залишив коментар, воркер вносить правки й пушить новий коміт.
12. Диспетчер надсилає в Slack підсумок: що зроблено, які перевірки пройдено, посилання на PR і джерела. Merge робить людина.

Якщо матеріали суперечать одне одному або бракує важливого рішення, агент ставить у Slack одне конкретне питання й чекає відповіді.

### Що отримує людина

- Зібраний контекст із посиланнями на джерела.
- Специфікацію, план і список задач зі статусами.
- Реалізовану зміну в окремій гілці.
- Результати перевірок і зауваження рев'юера.
- Draft PR із поясненням виконаного та відкритих питань.
- Повідомлення в Slack про CI, рев'ю та подальші дії.
- Видимий у адмінці стан задачі, логи сесій і консолі агентів.

## 6. Як влаштований прототип

### Архітектура простими словами

Jarvis складається з одного довгоживучого диспетчера й короткоживучих воркерів.

**Диспетчер** — це постійна інтерактивна сесія Claude Code. Саме з нею людина спілкується через Slack. Диспетчер не пише код: він приймає задачі, запускає воркерів, стежить за їхнім станом, ставить питання й повідомляє результат. Усе, що він знає, лежить на диску, тому після перезапуску він читає стан і продовжує з того ж місця.

**Воркер** — окрема сесія Claude Code на одну задачу, у своєму терміналі (tmux) і своєму worktree. Дві задачі означають два воркери, які не заважають один одному. Воркер проходить SDD-процес і залучає спеціалізованих субагентів.

**Watcher** — звичайний скрипт, який за розкладом перевіряє CI і рев'ю через GitHub. Поки нічого не змінилося, модель не запускається і ліміти підписки не витрачаються.

**Slack-канал** — невеликий MCP-сервер, який передає повідомлення зі Slack у сесію диспетчера і дає йому інструмент для відповіді. Це механізм каналів Claude Code (channels). Офіційного каналу для Slack немає, тому його пишемо самі.

**Адмінка** — веб-застосунок на основі Agent Ops Center. Показує задачі, стан, логи сесій і консолі агентів, щоб бачити, що відбувається, і дебажити.

```
Slack ⇄ slack-channel (MCP) ⇄ Диспетчер (claude, інтерактивна сесія)
                                   │  state.json · chats/*.md
                                   ├─→ Воркер 1 (claude у tmux, worktree A) → субагенти
                                   ├─→ Воркер 2 (claude у tmux, worktree B) → субагенти
                                   └─← Watcher (скрипт: CI і рев'ю PR через GitHub)
Адмінка (Agent Ops Center) ← стан, логи, консолі
```

### Складові

| Складова | Роль | Що показуємо |
| --- | --- | --- |
| Підписка Claude Code | Рушій для всіх ролей | Офіційний CLI `claude` під обліковим записом власника, без API-ключа |
| Диспетчер | Довгоживуча сесія, яка керує задачами | Прийом задачі, запуск воркерів, питання й повідомлення |
| Воркери | Виконання однієї задачі | Окремі сесії в tmux, окремі worktree, до двох паралельно |
| Спеціалізовані агенти | Ролі всередині воркера | Дослідник контексту, перевірка плану, виконавець, рев'юер |
| SOUL.md | Роль, принципи та стиль роботи агента | Коли агент уточнює задачу, як повідомляє прогрес |
| USER.md | Вподобання власника | Мова, деталізація, формат плану, підсумку та PR |
| Правила репозиторію | Проєктні конвенції | Архітектура, компоненти, команди перевірки |
| Claude Design | Джерело дизайну | Макет сторінки, з якого агент бере структуру й вигляд |
| Конектори Notion і Google Docs | Пошук і читання контексту | Структура курсу, правила подачі, вимоги до інтерфейсу |
| Стан | Продовження після перезапуску | `state.json`: задачі, етапи, гілки, PR, на що чекаємо; `chats/*.md`: контекст розмов |
| SDD-документи | Видимий процес виконання | context, spec, plan, tasks, result у папці задачі |
| Перевірки | Зворотний зв'язок | Тести, lint, typecheck; для інтерфейсу огляд у браузері |
| Watcher | Очікування CI і рев'ю | Опитування GitHub без моделі, пробудження диспетчера при зміні |
| Slack-канал | Інтерфейс задач і повідомлень | Задачі, питання, прогрес, підтвердження дозволів |
| Адмінка | Видимість і дебаг | Задачі, стан, логи, консолі агентів |

Усі ролі працюють на одному рушії та одній підписці. Розподіл ролей не вимагає кількох платних моделей.

### Структура стану на диску

```
jarvis/
  state.json            загальний стан: задачі, етапи, воркери, гілки, PR, очікування
  chats/<chat-id>.md    контекст розмови: що просили, що вирішили, відкриті питання
  tasks/<id>/           context.md, spec.md, plan.md, tasks.md, result.md, журнал подій
```

У `state.json` пише лише диспетчер. Воркери пишуть у свою папку задачі, а диспетчер переносить звідти статус. Так дві паралельні задачі не перезапишуть спільний файл.

### Персоналізація на конкретних прикладах

У SOUL.md описуємо: «перед реалізацією підготуй специфікацію», «звертайся з питанням, якщо відповідь змінює обсяг задачі», «показуй поточний етап».

У USER.md описуємо: «підсумки українською», «план коротким списком», «у фіналі дай посилання на джерела, список змін і результати перевірок».

Архітектурні обмеження та правила коду залишаємо в документації проєкту. Профіль власника визначає лише його вподобання.

## 7. Як показуємо Spec-Driven Development

Процес залишає артефакти, які учасники можуть відкрити:

- `context.md`: звідки взяли інформацію, які документи й дизайн використали, чого бракує.
- `spec.md`: що реалізуємо, межі задачі та критерії приймання.
- `plan.md`: як реалізуємо, які компоненти змінюємо та як перевіряємо.
- `tasks.md`: підзадачі зі статусами виконання.
- `result.md`: що зроблено, які перевірки пройдено та що залишилося.

Учасник бачить, як дизайн і знайдені джерела перетворюються на вимоги, вимоги на план, а план на зміни коду.

## 8. Що підготовлено заздалегідь, а що робимо в ефірі

Повну інфраструктуру не збираємо наживо: це забрало б увесь ефір і зробило б демо крихким. Готуємо робочий прототип заздалегідь, а в ефірі запускаємо його на реальній задачі й добудовуємо кілька частин, на яких добре видно принцип.

### Підготовлено до ефіру

- Навчальний репозиторій із CI, тестами й початковим станом застосунку.
- Дизайн сторінки в Claude Design.
- Матеріали в Notion і Google Docs, доступні учасникам для копіювання.
- Slack-воркспейс, Slack-застосунок і MCP-сервер Slack-каналу.
- Диспетчер: інструкції, запуск воркерів, робота зі станом.
- Воркер і спеціалізовані агенти: дослідник контексту, перевірка плану, виконавець, рев'юер.
- Шаблони SDD-документів.
- Watcher для CI і рев'ю PR.
- Налаштування дозволів для автономної роботи.
- Адмінка: задачі, стан, логи та консолі.
- Запасний запис повного проходу.

### Робимо в ефірі

- Заповнюємо SOUL.md і USER.md та показуємо, як одне правило змінює поведінку агента.
- Запускаємо диспетчера з каналом Slack і ставимо задачу.
- Відповідаємо на питання агента та підтверджуємо spec і план у Slack.
- Ставимо другу задачу паралельно й показуємо двох воркерів.
- Додаємо або змінюємо одну спеціалізовану роль, наприклад правило для рев'юера.
- Залишаємо коментар у PR і спостерігаємо, як агент його обробляє.
- Ламаємо один тест у CI й показуємо розбір падіння.
- Відкриваємо адмінку й розбираємо, що відбувається всередині: стан, логи, консолі.

Реалізація фічі займає 20–40 хвилин. Задачу ставимо на початку ефіру, а поки агент працює, розбираємо архітектуру й технічні челенджі. Якщо агент не встигає або ламається, переходимо на запис і прямо про це кажемо.

## 9. Сценарій живої демонстрації

1. Показуємо застосунок до змін, дизайн у Claude Design і матеріали в Notion та Google Docs.
2. Відкриваємо SOUL.md і USER.md, додаємо одне правило наживо.
3. Запускаємо диспетчера, у Slack ставимо задачу.
4. Агент відповідає в Slack: взяв задачу, створив гілку, показує, що шукає.
5. Поки він збирає контекст, пояснюємо архітектуру: диспетчер, воркери, стан, підписка.
6. Агент присилає spec і план. Відкриваємо `context.md` і `spec.md`, перевіряємо джерела вимог, підтверджуємо в Slack.
7. Ставимо другу задачу й показуємо двох воркерів у tmux та в адмінці.
8. Поки воркери працюють, розбираємо технічні челенджі (розділ 10).
9. Дивимося зміни коду, результати перевірок і рев'ю. Повторну спробу показуємо, якщо вона трапилась.
10. Відкриваємо готову сторінку, зіставляємо її з дизайном і spec, показуємо draft PR.
11. Показуємо, що CI ще виконується, а Jarvis зберіг стан і чекає.
12. Отримуємо в Slack повідомлення про результат CI.
13. Залишаємо коментар у PR, агент вносить правку, CI нового коміту стартує.
14. Ламаємо тест, показуємо розбір падіння та повідомлення в Slack.
15. Фінальне повідомлення: умови виконано, PR готовий до перегляду людиною.

Центральний момент демо: агент сам знайшов матеріали, застосував профіль власника, виконав задачу за видимим SDD-процесом і продовжив супровід після створення PR, а ми весь час бачили, що відбувається всередині.

## 10. Технічні челенджі, які розбираємо

Ці питання виникають у кожного, хто будує подібного агента. Розбираємо їх, поки агент працює, і показуємо рішення в коді PoC.

| Челендж | Чому виникає | Як вирішуємо в PoC |
| --- | --- | --- |
| Підписка замість API | Agent SDK і сторонні застосунки працюють через API-ключ; підставляти токен підписки в чужий код заборонено умовами | Оркестрація викликає лише офіційний CLI `claude` під обліковим записом власника. Один агент на одну підписку однієї людини |
| Ліміти підписки | Діє 5-годинне вікно й тижневий ліміт, кілька субагентів витрачають їх швидко | Watcher працює без моделі; модель запускається лише для змістовної роботи; ліміти спроб на кожен етап |
| Переповнення контексту диспетчера | Довга сесія накопичує історію, після стиснення губляться деталі | Диспетчер нічого не тримає «в голові»: стан у `state.json`, контекст у `chats/*.md`. Сесію можна перезапустити будь-коли |
| Slack-канал | Канали Claude Code в research preview, готові плагіни є лише для Telegram, Discord і iMessage | Власний MCP-сервер через Slack Socket Mode, без публічного URL. Запуск з `--dangerously-load-development-channels`, лише в інтерактивній сесії. Запасний варіант: офіційний плагін Telegram |
| Обмеження безкоштовного Slack | Не більше 10 застосунків, історія за 90 днів | Бот займає один слот; історія не потрібна, бо стан зберігається локально |
| Зв'язок диспетчера з воркерами | Воркер — окремий процес, у нього своя сесія | Задачу передаємо через файли задачі й команду в tmux; результат воркер записує у свою папку. Механізм фіксуємо під час підготовки |
| Паралельні задачі | Дві задачі в одній робочій копії конфліктують у файлах, портах і залежностях | Окремий git worktree і гілка на задачу; окремі порти для dev-сервера й тестів |
| Дозволи без людини | Кожен запит дозволу зупиняє сесію, поки людина не відповість | Дозволені команди задаємо в налаштуваннях; решту запитів пересилаємо в Slack з підтвердженням `yes <id>` / `no <id>`. Merge і небезпечні дії лишаються за людиною |
| Нагляд за CI з ноутбука | Webhook від GitHub не дійде до ноутбука без публічної адреси | Watcher опитує GitHub за розкладом і передає подію диспетчеру через локальний канал. Після сну ноутбука добирає пропущені статуси |
| Ноутбук засинає | Разом із ним зупиняються диспетчер і watcher | На час довгих задач `caffeinate`; після пробудження watcher порівнює зі збереженим станом |
| Коментарі в PR | Агент може реагувати на чужі коментарі або на власні й зациклитися | Обробляємо лише коментарі від дозволених людей, адресовані агенту; ліміт раундів правок |
| Prompt injection | Текст зі Slack, PR, Notion чи логів CI потрапляє в контекст моделі | Allowlist відправників у Slack-каналі; зовнішній вміст вважаємо даними, а не інструкціями; права на запис мінімальні |
| Конектори у воркерах | Notion і Google Docs мають бути доступні в сесіях, які запускає диспетчер | Підключаємо через MCP і перевіряємо доступ у воркері до ефіру |
| Дизайн із Claude Design | Воркеру потрібен дизайн у форматі, який він може прочитати | Передаємо дизайн через handoff у Claude Code. Формат перевіряємо під час підготовки |
| Видимість і дебаг | Коли працюють кілька сесій, незрозуміло, що де відбувається | Адмінка: стан, журнал подій, логи сесій через хуки Claude Code, живий перегляд консолей у tmux |
| Стабільність демо | Агент працює 20–40 хвилин і може помилитися | Задача стартує на початку ефіру; є запасний запис; помилки показуємо як частину розбору |

## 14. Готовий опис для анонсу

**Власний AI-агент для розробки: від задачі до перевіреного pull request**

Дизайн у Claude Design, вимоги в Notion, рішення в Google Docs, код і правила в репозиторії. Щоб делегувати задачу AI, цей контекст доводиться збирати вручну, а потім ще й стежити за CI та рев'ю.

На практичному вебінарі покажемо, як зібрати proof of concept персонального агента на підписці Claude Code. Він приймає задачу в Slack, сам знаходить потрібні матеріали та доводить задачу до перевіреного PR.

Налаштуємо роль агента й ваші вподобання, підключимо джерела та пройдемо Spec-Driven Development workflow: від зібраного контексту й специфікації до плану, реалізації, перевірок і draft PR. Поки агент працює, розберемо технічні рішення: як обійтися без API, як вести дві задачі паралельно, як агент чекає CI і не витрачає ліміти.

**На вебінарі ви побачите:**

- Як агент бере дизайн із Claude Design і знаходить контекст у Notion, Google Docs і репозиторії.
- Як описати його роль, принципи роботи та бажаний формат результатів.
- Як перетворити знайдені вимоги на специфікацію, план і підзадачі.
- Як диспетчер і спеціалізовані агенти ведуть кілька задач паралельно.
- Як агент стежить за CI та рев'ю, виправляє зауваження й пише вам у Slack.
- Як бачити, що відбувається всередині агента, і дебажити його.

**Після вебінару ви отримаєте** стартовий PoC, шаблони профілю й SDD-документів та інструкцію для повторення демонстрації зі своєю підпискою й доступами.

Підійде розробникам, які починають працювати з агентами, і тим, хто вже зібрав першу автоматизацію та хоче поєднати контекст, персоналізацію й виконання задач у власному воркфлоу.

## 15. Пояснення для відділу продажів

**Що це за агент?**

Персональний агент для кодових задач. Йому пишуть задачу в Slack із посиланнями на дизайн і матеріали. Він збирає контекст, оформлює специфікацію й план, залучає потрібні ролі та готує зміни до PR. Далі стежить за CI й рев'ю, виправляє зауваження та повідомляє власника.

**Чи треба платити за API?**

Ні. Агент працює через підписку Claude Code (Pro або Max) на комп'ютері власника. Обмеження: ліміти підписки та правило «одна підписка — одна людина».

**У чому користь, якщо людина вже має агента?**

Можна побачити, як поєднати зовнішні джерела, власні вподобання, SDD, паралельні задачі й нагляд за CI, а також які технічні проблеми виникають на цьому шляху. Учасник зможе дослідити код PoC і взяти потрібні частини у свої експерименти.

**Що означає long-running task?**

Задача може чекати зовнішньої події: завершення CI, рев'ю чи відповіді користувача. Jarvis зберігає стан на диску, окремий скрипт перевіряє події, і модель запускається лише тоді, коли є що робити.

**Що означає персоналізація?**

Профіль визначає роль і стиль роботи агента, а налаштування власника описують мову, деталізацію, формат плану та фінального результату. Правила проєкту зберігаються окремо.

**Чи потрібен платний Slack?**

Ні. Бот працює на безкоштовному воркспейсі й займає один із десяти дозволених застосунків.

**Чи потрібні корпоративні документи?**

Для повторення готуємо демонстраційні матеріали й дизайн, які можна скопіювати у власні облікові записи. Для своїх задач учасник використовує джерела, до яких має доступ.

**Чи буде це готова система для компанії?**

Ні, це навчальний PoC для однієї людини. Командне використання, другий рушій і нагляд за довгими джобами описані як наступні кроки.

## 18. Довготривалі задачі та повідомлення

### Нагляд за PR і CI

Приклад команди в Slack:

> Стеж за цим PR. Повідом, коли всі перевірки для актуального коміту завершаться, коли рев'юер попросить зміни або коли буде отримано схвалення.

Jarvis зберігає умови нагляду й посилання на PR. Статуси CI та рев'ю відстежуються окремо: успішні тести не означають людського схвалення.

Приклад послідовності:

1. PR відкрито, CI виконується, рев'ю ще не завершено.
2. CI завершився. Jarvis повідомляє фактичний результат.
3. Якщо CI червоний, воркер читає лог, пробує виправити й пушить новий коміт.
4. Рев'юер залишає зауваження. Jarvis показує їх і вносить правки.
5. Після push відстежуються перевірки нового коміту.
6. Отримано потрібний стан рев'ю. Jarvis повідомляє, що умови виконано. Рішення про merge приймає людина.

Приклади повідомлень:

- «PR створено. CI виконується, очікую результатів».
- «Перевірки поточного коміту пройдено. Людське рев'ю ще очікується».
- «CI впав на `course-page.spec.ts`. Причина: змінився селектор. Виправляю».
- «Рев'юер залишив два зауваження. Готую виправлення».
- «Правки додано. CI нового коміту виконується».
- «Перевірки пройдено, отримано схвалення. Можна переходити до вашого фінального перегляду».
- «Після трьох спроб задача зупинена. Ось помилка, виконані дії та питання».

### Як працює очікування

- Watcher перевіряє статуси через GitHub API за розкладом.
- Стан зберігається на диску окремо від розмови з моделлю.
- Відсутність змін не породжує повідомлення чи запуск моделі.
- Модель залучається, коли треба дослідити помилку, опрацювати зауваження або підготувати підсумок.
- Зберігаються остання оброблена подія, умови повідомлення та ліміти спроб.
- Завершення, питання людині й вичерпання ліміту є окремими станами.
- Нагляд працює, поки ноутбук не спить. Після пробудження watcher добирає пропущені статуси.

### Нагляд за довгими джобами

У вихідному Jarvis передбачено нагляд за backfill, міграціями, нічними пайплайнами й релізами. У PoC цього немає: описуємо як наступний крок, бо механізм той самий, що й для CI, змінюється лише джерело статусу.

## 19. Повна карта можливостей Jarvis

Цільовий концепт. Колонка «PoC» показує, що входить у прототип для вебінару.

| Частина Jarvis | Що містить | PoC |
| --- | --- | --- |
| Входи | Slack, тікет, CI-подія, алерт, команда нагляду, розклад | Slack і CI-подія |
| Task → PR | Уточнення, контекст, план, worktree, перевірки, повторні спроби, AI-рев'ю, draft PR | Так |
| Дизайн як вхід | Макет із Claude Design | Так |
| Продовження PR | Коментарі, доопрацювання, повторний контроль CI | Так |
| Context search | Пошук у Notion, Google Docs, Slack, тікетах, відповіді з джерелами | Notion і Google Docs |
| Знайдені знання → дія | Перетворення відповіді на документацію або кодову задачу | Ні |
| CI triage | Аналіз логів і diff, flaky чи регресія, наступна дія | Для власних PR |
| Long-running watch | Джоби, міграції, backfill, пайплайни, релізи | Ні, наступний крок |
| Паралельність | Кілька задач одночасно | До двох задач |
| Персональний home | SOUL.md, USER.md, пам'ять, журнали задач | SOUL, USER, журнали |
| Стан виконання | Задачі, сесії, спроби, статуси, питання, події | `state.json` і файли задач |
| Адмінка | Задачі, стан, логи, консолі, дебаг | Так, на основі Agent Ops Center |
| Рушії | Claude Code; Codex як другий worker або reviewer | Лише Claude Code |
| Персональні зміни | Пам'ять і пропозиції нових правил з підтвердженням | Ні |
| Контроль виконання | Ліміти спроб, часу й викликів; передача людині | Ліміти спроб |
| Доступи | Окремі права на читання й запис, журнал дій | Allowlist у Slack, дозволи Claude Code |
| Командний розвиток | Спільні канали, кілька людей, аудит | Ні |

### Послідовність розвитку

1. Slack-канал, диспетчер і воркер; задача до PR з перевірками та збереженням стану.
2. Конектори, Claude Design і нагляд за CI.
3. Паралельні задачі й адмінка.
4. Нагляд за довгими джобами.
5. Другий рушій, персональна пам'ять і пропозиції змін поведінки.
6. Командне використання.

У вебінарному PoC показуємо кроки 1–3. Решта залишається в карті розвитку.

### Що перевіряємо перед реалізацією

- Механізм каналів Claude Code і прапорець для власного каналу: вони в research preview і можуть змінитися.
- Socket Mode на безкоштовному тарифі Slack.
- Доступ до конекторів Notion і Google Docs із сесій, які запускає диспетчер.
- Формат передачі дизайну з Claude Design у Claude Code.
- Актуальні ліміти підписки на повному прогоні двох задач.

Приклади Slack-повідомлень і метрики інших компаній з оригінального концепту є ілюстраціями. Не представляємо їх як результати нашого PoC.
