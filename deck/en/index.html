Tool · secrets

Infisical: one store that gives the laptop and the server the same secrets

What it is

An open-source secrets store

A web UI and a CLI: secrets are stored encrypted, with change history and access rights. We use the cloud version, but you can also self-host it.

4 concepts
  • Project: we have one, jarvis
  • Environment: dev for the laptop, prod for the server
  • Secret: a name–value pair, same names as in .env.example
  • Machine identity: a non-human account for the server
How we use it
  • Laptop: infisical login with your own account
  • Server: a machine identity, read-only on prod
  • Launch: with-secrets.sh logs in and calls infisical run: values go into the process environment, never to disk
What we gained
  • One source for the laptop, the rehearsal container and the server
  • Rotation: change the value and restart jarvis-engine
  • compose.yaml and systemd hold no values at all, only variable names
What it cost
  • Without Infisical the engine won't start (processes already running are unaffected)
  • One more external account
  • The only secret on the server's disk: the machine identity's client secret, /etc/jarvis/infisical.env, root, 0600

Problem P01

The agent has to work without a human, but the API bills every token, and a subscription is meant for a human in the CLI.

What we chose. claude -p with stream-json: the official CLI on a subscription, every event arrives as JSON, limits are set with flags.

What we rejected and why

  • Agent SDK with an API key: a separate bill, the subscription doesn't apply. Anthropic doesn't allow the SDK under a claude.ai login (ADR-0003)
  • Interactive session and channels: research preview, workers in tmux, no structured log (ADR-0003)

The cost

A run's cost is only visible at its end.

Where to look

ADR-0003 · engine/src/infrastructure/claude/

Problem P02

A model session doesn't survive a restart, and context compaction quietly drops what the agent “remembered”.

What we chose. Postgres and a state machine in the engine: after a restart the engine reads the database and carries on. The model changes state only through MCP tools.

What we rejected and why

  • State in the model session: restarts and compaction lose it
  • state.json and files: the journal and run events are tables (ADR-0008)
  • SQLite: the owner wanted Postgres in Docker (ADR-0008)

The cost

Development needs Docker.

Where to look

ADR-0008 · engine/src/domain/task.ts

Problem P03

What the agent hasn't read doesn't exist for it. And a long search uses up the context window before any code gets written.

What we chose. The context-researcher subagent reads sources via MCP separately, so the worker's window stays clean. Every requirement links to its source.

What we rejected and why

  • Pasting context by hand: the human becomes the bottleneck
  • A RAG index over all docs: the index has to be kept fresh, so we skipped it

The cost

Quality depends on how well the docs are written.

Where to look

agent/agents/context-researcher.md · docs/architecture/connectors.md

Problem P04

Before ADR-0022 the engine trusted report_checks(passed: true), and a PR got opened even when checks were red.

What we chose. open_pr: the engine runs the checks and refuses on red. The reviewer and ui-tester come on top. Nothing can bypass it: the worker has no GitHub token.

What we rejected and why

  • A rule in the prompt: a promise, not a guarantee
  • Pre-push hook: lives in the repo the worker can change
  • GitHub required checks only: don't stop a red push (all ADR-0022)

The cost

Check commands are fixed up front, when the spec is approved.

Where to look

ADR-0022 · docs/plans/engine-side-checks-and-pr.md

Problem P05

Merge, push to main, rm -rf, sudo: one such action costs more than all the hours saved.

What we chose. A deny-list and tools per role: Bash is allowed, irreversible actions aren't, anything doubtful goes to the owner as a card. Since 11.11, UI checks also run in a throwaway container.

What we rejected and why

  • Narrow Bash(cmd:*) permissions: a single && raised a card and the run hung. Removed after T-3
  • A blacklist of strings: easy to bypass, yet people trust it (ADR-0022)

The cost

The list needs upkeep. So far the container covers only UI checks.

Where to look

agent/settings/worker.json · ADR-0026

Problem P06

A secret that lands in the model's context, a log or a chat is considered compromised.

What we chose. Infisical and an env allow-list: one source of secrets, a worker with no token, the child claude sees only allowed variables.

What we rejected and why

  • A hand-edited .env: went stale, which led to “Bad credentials” (ADR-0015)
  • A token in a URL or config: ended up in .git/config, fixed on 08.11

The cost

Without Infisical the engine won't start. A separate uid for child processes isn't done yet.

Where to look

ADR-0015 · scripts/with-secrets.sh

Problem P07

A task takes 20–40 minutes. Close the laptop lid and the work stops. You can't approve a spec from your phone either.

What we chose. A Hetzner VPS and a private Tailscale network: access from all your devices, 0 inbound ports.

What we rejected and why

  • Keep it on the laptop: sleep stops the task
  • A VPS with a public address: the UI and subscription login are exposed to the internet
  • GitHub App and a webhook via a tunnel: needs a public address or a tunnel (ADR-0007)

The cost

No webhook, so the watcher polls GitHub. The first live task on the server hasn't run yet.

Where to look

ADR-0016 · docs/architecture/deployment.md

Problem P08

Prompt injection: an order in a review comment or a CI log looks just like an instruction from the engine.

What we chose. The engine wraps untrusted text in <untrusted-content>. The prompts say not to follow the order but to report the attempt to the owner.

What we rejected and why

  • Only a rule in the prompt: not enough for text we assemble ourselves (ADR-0017)
  • An order filter: no filter detects them reliably, and it mangles comments (ADR-0017)
  • Dual LLM / CaMeL: more complex and more runs, so we skipped it

The cost

Text the model fetches by itself can't be wrapped by the engine.

Where to look

ADR-0017 · engine/src/application/conversation/untrusted.ts

Problem P09

What the agent figured out during a task is lost when the run ends. The next task repeats the same mistakes.

What we chose. One USER.md file with a ## Learned section. Each entry has a date and counts of confirmations and refutations. Nothing disappears by itself.

What we rejected and why

  • An approval card per entry: the owner becomes the bottleneck
  • A raw log and a distiller run: costs an extra run and has to guess at duplicates
  • Split across 3 files: 3 write paths (all ADR-0021)

The cost

Not tried on a live task yet, only in tests.

Where to look

ADR-0021 · docs/plans/agent-memory.md

Problem P10

On a subscription no bill arrives to raise the alarm. A runaway loop quietly eats the limits.

What we chose. Limits in the config and CLI flags: --max-turns, --max-budget-usd, a daily token limit. Every event is visible in the console, metrics go to Grafana.

What we rejected and why

  • No limits: the first runaway loop eats the day
  • Limits in env or in the DB via UI: easy to change, one more dependency (ADR-0005)

The cost

Cost is only visible at the end of a run. The CLI gives no per-subagent breakdown.

Where to look

ADR-0005 · ~/.jarvis/jarvis.config.json · Usage page

Safeguard

The engine won't start with an API key

If it sees ANTHROPIC_API_KEY or ANTHROPIC_AUTH_TOKEN, it refuses to run. It also strips these variables from the environment of child processes.

1 subscription, 1 person. You log in once with the claude command.

Brake

The budget is a counter, not a bill

  • 120 turns and $10 per run
  • 50M tokens per day, 120 min per task
  • 1 slot on a laptop, 3 on a server
  • 3 check attempts, 2 CI rounds, 3 reviews

The daily limit is in tokens: the CLI's dollar figure is an estimate for the whole session, not for a single run.

Problem 05 · 6 safeguards

The agent works on its own, within 6 rules

Permissions

A deny-list instead of an allow-list

Bash is allowed; git push, gh, rm -rf, sudo, git reset --hard are banned. Anything else questionable goes to the owner as a card.

Untrusted text

A PR comment is data, not an order

The engine wraps external text in an <untrusted-content> tag. If the agent sees an instruction inside, it stops and asks the owner.

Repositories

Clones only from an allow-list

An explicit list of owner/name, or “any repository in my account”. Jarvis's own repository is a target only with the repos.allowSelf flag, which is off and can't be turned on from chat.

Checks

The engine runs the tests, not the model

Commands are frozen when the spec is approved. On red the PR won't open, unless main is red the same way. The exact commit that was checked is the one pushed.

Limits

Every loop has a limit

Turns, budget per run, tokens per day, time per task, fix rounds, 100 commits and 100 PR comments a day. At the limit the task stops with an explanation.

Human

A human always does the merge

The agent has no tool that merges, pushes to the base branch or deletes a branch. The PR is always a draft.

Problem 06 · our mistakes

These rules came from 5 of our own mistakes

1Secrets live only in Infisical. .env is an export, not a second source.
2Committed files hold variable names only. Compose won't start without a value.
3No tokens in URLs or config. A credential helper reads the token on each use.
4The worker has no GitHub token. The engine pushes and opens PRs.
5On the server only root reads the secret. The agent user isn't in the docker group.
6A child process gets its environment from an allowlist.
7A secret that passed through a chat or log gets rotated.

None of them caused a leak. Each was caught by an audit or by the first live run.

08.11 · found after the first live task

On-demand cloning baked https://x-access-token:<token>@… into the origin URL. The token sat in plain text in .git/config for the life of the clone: git remote -v shows it, and so does any output pasted into a bug report, or a backup.

What we did: the URL is clean; a credential helper reads the token from the environment. Old clones are fixed on next use. And since ADR-0022 the worker has no token at all.

08.11 · security audit, severity High

compose.yaml held a literal Postgres password, jarvis. Any process on the host could connect to 127.0.0.1:5433 and rewrite Jarvis's state, including permission decisions.

What we did: the password is generated and lives in Infisical. Compose takes it from the environment and refuses to start without it.

10.11 · found on the jarvis-01 server

The jarvis user was in the docker group. That is effectively root: any child claude with Bash could mount the host disk into a container and read /etc/jarvis/infisical.env.

What we did: removed the user from the group. The runbook now forbids it; only root runs Docker.

08.11 · the “Bad credentials” error

It looked like a bad token. Actually the GITHUB_TOKEN= line in ~/.jarvis/.env was empty, so the container got nothing. The second source had drifted from the first without anyone noticing.

What we did: the token comes from Infisical. We regenerate .env with infisical export and never edit it by hand.

10.11 · during server setup

The client secret of the Infisical machine identity passed through a chat with an assistant. Technically that's not a leak, but we no longer control where that text is stored.

What we're doing: rotating it. Anything that's been in a chat, log or screenshot counts as compromised.

Problem 07 · what a tailnet gives

A tailnet locks down access to the server, but doesn't replace the safeguards inside it

What it gives
  • A private HTTPS address. The UI opens from laptop and phone, and the internet can't see it.
  • SSH with no open port. Log in via tailscale ssh; port 22 can be closed in the firewall.
  • Phone as a remote. Approve a spec or answer the agent on the go.
  • The subscription login stays hidden. It lives on the server, and only the owner's devices are in the tailnet.
  • Losing the tailnet means losing access, not data.
What it doesn't
  • Notifications. Nothing tells you a card is waiting. Slack adds this in iteration 2.
  • Protection from the agent itself. What it does inside the server is limited by permissions and allowlists, not the network.
  • Inbound webhooks. That's why we poll PR status instead of receiving it.
  • Backups. The host holds state: the database, ~/.jarvis, ~/.claude. Daily Hetzner snapshots cover them.
